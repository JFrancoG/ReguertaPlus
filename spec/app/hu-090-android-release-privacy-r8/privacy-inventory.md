# Privacy inventory - HU-090

## 1. Scope and evidence status

- Reviewed on 2026-11-10 against the local HU-090 Android implementation.
- This is a **source-backed inventory for review**, not a completed Google Play
  Data Safety declaration, runtime consent attestation, or legal assessment.
- The owner-approved product policy retains non-advertising Analytics usage
  reporting, measurement and attribution, Crashlytics, and FCM. Advertising
  identifiers, advertising uses, and personalized advertising remain disabled.
- The inventory covers the telemetry, authentication, authorized-device and
  device-registration storage surfaces below. The complete app's functional
  data inventory remains a separate prerequisite for Data Safety.
- No Firebase Console settings, production services, real credentials, user
  records, runtime traffic, or persisted consent state were inspected for this
  review. No build or UI execution was performed for this inventory.

Read with the [approved plan](plan.md), [specification](spec.md), and
[tasks](tasks.md). Artifact permission/default checks belong to the local
validation evidence; they do not establish the runtime observations excluded
above.

## 2. Advertising controls and preserved measurement

The main [Android manifest](../../../android/Reguerta/app/src/main/AndroidManifest.xml)
removes these permissions at the manifest merge boundary:

- `com.google.android.gms.permission.AD_ID`
- `android.permission.ACCESS_ADSERVICES_AD_ID`
- `android.permission.ACCESS_ADSERVICES_ATTRIBUTION`

It also provides literal `false` values before automatic SDK initialization for
`google_analytics_adid_collection_enabled`,
`google_analytics_default_allow_ad_storage`,
`google_analytics_default_allow_ad_user_data`, and
`google_analytics_default_allow_ad_personalization_signals`.

These keys follow the supported Android controls in
[Configure Analytics data collection](https://firebase.google.com/docs/analytics/android/configure-data-collection)
and [Set up app consent mode](https://developers.google.com/tag-platform/security/guides/app-consent?platform=android).
Disabling personalized advertising does not disable ordinary measurement or
attribution. HU-090 preserves the existing non-advertising Analytics collection
and consent policy: it adds no `analytics_storage` grant and no new consent UI.

A source scan of `app/src/main`, `app/src/release`, and `app/src/debug` found no
application calls to `setConsent`, `setAnalyticsCollectionEnabled`,
`setUserProperty`, `setUserId`, or `logEvent`, and no `AdvertisingIdClient` use.
Advertising-key matches were limited to the manifest controls above. This is
evidence that the reviewed first-party source contains no later application
path re-enabling advertising; it is not proof of all SDK internals or effective
runtime consent.

The SDK documents that `setConsent` overrides defaults and persists across app
executions. Historical consent preferences have not been verified. Console-side
Google Signals, linked Ads accounts, exports, and data-sharing settings have not
been verified either. No cloud configuration changes or declarations are
authorized by this document.

## 3. Remaining non-advertising data and identifiers

### Analytics

The [app dependencies](../../../android/Reguerta/app/build.gradle.kts) retain
`firebase-analytics` under the selected Firebase BOM. The main manifest neither
permanently deactivates Analytics nor disables its collection globally.

The [official Analytics disclosure guide](https://support.google.com/analytics/answer/11582702?hl=en)
describes an app-instance ID, app lifecycle events such as sessions and screen
views, and coarse location derived from masked IP addresses. No custom
Analytics user ID or custom event/property calls were found in the reviewed
first-party source. The absence of advertising IDs therefore does not mean
anonymous usage or absence of collection. Actual events and collection behavior
have not been observed in this review.

### Crashlytics and Firebase Sessions

The [app dependencies](../../../android/Reguerta/app/build.gradle.kts) retain
`firebase-crashlytics`. There is no runtime collection-disable flag in the main
manifest. Release's `mappingFileUploadEnabled = false` prevents the build-time
mapping upload; it does not disable runtime crash collection.

The [Firebase disclosure guide](https://firebase.google.com/docs/android/play-data-disclosure#crashlytics)
documents crash stack traces, relevant app/device state, a Crashlytics
installation UUID, and Analytics breadcrumbs. Its transitive Firebase Sessions
component records app/device metadata and session usage for quality metrics.
No first-party custom Crashlytics user IDs, custom keys, or non-fatal report
calls were found in the reviewed source. Reports may still contain diagnostic
information generated by the SDK and by failures; report contents were not
inspected.

### Firebase Installations and Cloud Messaging

The main manifest retains
`firebase_messaging_installation_id_enabled = true` and the Messaging service.
The production
[registration provider](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/FirebaseAuthorizedDeviceRegistrar.kt)
calls `FirebaseMessaging.register()` and obtains
`FirebaseInstallations.id`. The
[Messaging service](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/ReguertaFirebaseMessagingService.kt)
handles refreshed installation registrations.

FID is an installation identifier used by the SDK, distinct from an advertising
ID. The [official Installations and Messaging disclosure sections](https://firebase.google.com/docs/android/play-data-disclosure#installations)
must be considered alongside the app's own use and association of FID below.
This review did not send notifications or verify delivery, token lifecycle, or
server configuration.

### Firebase Authentication

The
[authentication adapter](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/access/FirebaseAuthSessionProvider.kt)
uses email/password sign-in and account creation, email verification, password
reset, and ID-token refresh. Its session snapshot contains UID, email and
email-verification state. The
[authenticated Functions client](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/access/AuthenticatedFirebaseFunctionsClient.kt)
obtains the current Firebase ID token for authenticated requests.

The [official Authentication disclosure section](https://firebase.google.com/docs/android/play-data-disclosure#authentication)
also describes SDK-level security and account data. SDK-managed authentication
storage, actual server retention, and account-deletion behavior were not audited
here. No real UID, password, ID token, or persisted session value was read.

### Authorized-device records in Firestore

The
[device registrar](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/FirebaseAuthorizedDeviceRegistrar.kt)
constructs a record containing the app-generated `deviceId`, platform, app
version, OS version, API level, manufacturer, model, FID, and registration/usage
timestamps. The
[Firestore repository](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/FirestoreDeviceRegistrationRepository.kt)
stores it under the member's `devices/{deviceId}` document and updates the
member's `lastDeviceId`. This associates the installation and device metadata
with an authorized member; it must not be described as unlinked anonymous data.

The modern Android write explicitly sets legacy `fcmToken` and `tokenUpdatedAt`
fields to `null` and stores `firebaseInstallationId` instead. This is a source
contract for new writes, not evidence that all historical backend records have
been removed or migrated. Session-generation/current-authorization fences guard
the write; their presence does not replace retention/deletion review.

### Device-registration secure store

[DeviceRegistrationPreferences](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/DeviceRegistrationPreferences.kt)
generates and persists an app-specific random UUID for `deviceId`. It also
stores FID and the authorized context: `memberId`, `authUid`, environment and a
random `leaseId`. Clearing the authorized session removes that context; it does
not automatically remove the installation identifiers.

The
[AndroidKeyStore-backed implementation](../../../android/Reguerta/app/src/main/java/com/reguerta/user/data/devices/AndroidKeystoreDeviceRegistrationStore.kt)
encrypts values using AES-GCM, with the preference key as authenticated data and
a 256-bit AES key generated in AndroidKeyStore. This establishes the source
design, not verified hardware backing on every supported device.

The app excludes both current and legacy device-registration preference files
from [backup](../../../android/Reguerta/app/src/main/res/xml/backup_rules.xml) and
[cloud backup/device transfer](../../../android/Reguerta/app/src/main/res/xml/data_extraction_rules.xml).
These exclusions cover those named files; they are not evidence about every
SDK-owned file or the app's complete local storage.

## 4. Data Safety review still required

The inventory supports preparation of the disclosure. It does not select final
Console answers. Before submitting them:

1. Complete the functional-data inventory for the whole app, including member
   profiles and contact data, roles, orders/history, commitments/shifts,
   notifications, and any uploaded media or other user content actually used.
   The [Member model](../../../android/Reguerta/app/src/main/java/com/reguerta/user/domain/access/Member.kt)
   alone includes name, optional company/phone, email, UID and membership data;
   it is not a complete data-flow audit.
2. Map actual data flows to current Play categories and purposes. Candidate
   areas include device/other IDs, user IDs and contact data, app activity,
   diagnostics and coarse location. Distinguish Analytics analysis,
   Crashlytics diagnostics, Messaging functionality, and authentication/device
   authorization purposes. Do not infer an advertising purpose merely because
   a Firebase SDK is present.
3. Confirm optional Analytics settings, linked products, exports and data
   sharing with the owner against the real configuration when that inspection
   is authorized. Determine collection versus sharing under the applicable
   Play definitions and service arrangements; do not infer the answer solely
   from network destinations or SDK names.
4. Verify retention, deletion/account-deletion paths, optional versus required
   collection, security statements and privacy-policy wording against actual
   behavior and operating practices. Source encryption controls alone do not
   prove every transport/storage claim for every app flow.
5. Reconcile this draft with the final dependency graph and artifact evidence.
   Any authorized runtime or exact-artifact cloud validation must record its
   own scope and results separately; local QA substitutes are not proof of
   production telemetry or the production artifact's complete behavior.

Use the [Firebase SDK disclosure guide](https://firebase.google.com/docs/android/play-data-disclosure)
and [Analytics disclosure guide](https://support.google.com/analytics/answer/11582702?hl=en)
as SDK inputs, together with the app's own flows. Neither this inventory nor
permission removal constitutes a completed privacy review, a finding of legal
consent, or approval to publish.
